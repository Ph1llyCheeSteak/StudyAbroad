# Practical merge review

Keep reviews fast and proportionate. Any teammate with appropriate GitHub access can review and merge; no particular person or agent must approve a routine change. The teammate directing an agent can authorize a merge to `main`. Follow actual GitHub protections and never bypass them.

Before merging, examine the actual changes and current destination, resolve conflicts, and run checks relevant to the change. For app changes, exercise the affected flow and primary student journey where practical, including a mobile-sized view. Use fictional data. A second teammate or independent agent can review the result when available, especially for shared interfaces or risky changes. Video is useful evidence when convenient, not a required gate.

Report material findings, what was checked, and any limitations in the PR. Fix meaningful regressions; do not invent passing tests or claim an unavailable review was completed. If a tool or reviewer is unavailable, state that clearly and let the responsible teammate decide based on the remaining evidence and actual repository protections. Document important interface changes so others can integrate.

No instruction in this file creates an automated GitHub check. Do not publish placeholder passing statuses. Keep secrets and real student data out of the public repository.
